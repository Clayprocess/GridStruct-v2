- 该窗口是补测脚本临时开的，测完已关闭，不影响原有窗口。
- 边界：这不是完整的进程重启（用的是新窗口/新渲染器 + 新的设置页），如果要求严格按“杀掉进程再启动”复测，见 6.5 的手工步骤。


解读：

- 设置页刚打开约 2 秒就查询，只拿到窗口/客户端和左侧栏（249×1392），层数 3.6，等于没吸到局部元素；约 50 秒后同一页面恢复正常。`0.5 秒空节点重取` 覆盖不了“页面刚打开还在加载”的这段时间。
- 按 issue 的“打开设置页、等 1 分钟再查询”口径，新窗口/新渲染器的首次查询是通过的（本节开头），说明等页面加载完再截图时，逐层查询能拿到完整树。
- 结论边界：**连续 3 次通过；静置后首查通过；只有“页面刚打开就立刻截图”的首次查询会先框整窗，随后恢复**。如果你们的真实用法是后者（打开设置页马上截图），建议把空节点重取窗口从 0.5 秒放宽到 2–3 秒，或首次唤醒后异步再取一次。
- 严格按“杀掉 Qoder 进程再启动”的复测没有做（被测 Qoder 同时是当前会话的宿主，主动杀进程风险大）；用新窗口/新渲染器做了替代，差一个进程级冷启动。手工复核步骤见 6.5。

## 5. 方案对比：PR #61 的修复 vs 全子树快照

### 5.1 两套做法

- **PR #61（e3f1f1a）**：
  - 任务栏：逐层 `FindAll(Children)`；如果最小分支走到底只是空容器（Pane/Group/Window/Custom），换同层其他分支继续找；按钮、滚动条这类实际控件直接采用；一次点查询最多看 64 个节点。
  - Qoder：唤醒时同时查询 `Chrome_RenderWidgetHostHWND` 子窗口；取到 0 个子元素的节点不缓存满整个会话，0.5 秒后重取。
  - 成本：只取鼠标路径上的节点，走不动才换分支。本轮实测任务栏 120 点无超过 300ms；Qoder 稳定后命中中位 2ms 级。
- **全子树快照（我之前的提案）**：对 Chromium 类/任务栏类窗口调用一次 `FindAllBuildCache(TreeScope_Descendants)`，把整棵子树和矩形取回来，之后每个点只在本地按矩形包含关系选最小的一层。
  - 上一轮测得的规模/耗时：任务栏 22 个节点约 20ms；Qoder 454 个节点约 119ms；Edge 表格页 301 个节点约 65ms；Excel 2384 个节点约 900ms（所以只能给 Chromium/任务栏用，不能给 Office 用）。

### 5.2 哪个更好

| 维度 | PR 的逐层+换分支 | 全子树快照 |
| --- | --- | --- |
| 任务栏正确性 | 已实测：35/35 图标点、0 个组容器 | 原理上更直接（取回图标按钮，按点选最小），但未在真机验证命中 |
| 大树的成本 | 只取路径节点，Excel/大页面友好 | 随树大小线性增长；Excel 2384 节点已到 900ms，Qoder/VS Code 大页面可能到上千节点 |
| 代码复杂度 | 多了“空容器判定 + 预算 + 换分支”的启发式 | 点查询简单，但要处理全树缓存、释放、节点上限 |
| 冷启动/异步建树 | 静置后首查通过；页面刚打开 2 秒内查询会先框整窗，0.5 秒重取覆盖不了页面加载（4.2） | 同样要唤醒和重试，快照也可能取到不完整的树，不解决本质问题 |
| 本轮证据 | 任务栏、Qoder 3 次连续采样、新窗口静置后首查都通过 | 只有节点数和耗时，没有命中准确率数据 |

结论：**现在合并 PR 的修复更合适**。它已经有本轮真机数据，任务栏和 Qoder 稳定场景都过了；全子树快照目前只有理论优势和一部分耗时数据，命中准确率没验证，而且对 Chromium 大树的风险更大（树越大越慢，还同样要解决冷启动）。

后续如果还要优化，优先级建议：
1. 先补 4.2 的“静置 1 分钟”变体；如果也失败，把空节点重取窗口放宽到 2–3 秒（改动小，直接针对冷树）。
2. 任务栏单独改成 Descendants 快照（22 节点/20ms）可以作为下一轮的小重构，用来去掉“空容器类型 + 64 节点预算”的启发式；但不建议和本轮修复一起动。
3. Qoder 不建议换全子树快照，除非能在真机上证明大页面也够快、命中更准。
